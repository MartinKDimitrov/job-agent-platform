# LLM & разходи — стратегия

Цел: максимална пестеливост. Изводът накратко: **90% от системата не се нуждае от скъп
LLM.** Скъпото (генеративен LLM) е само CV/cover-letter и по избор „обяснение на скора".
За тях — **BYOK (потребителят си ползва собствен ключ)**, с безплатен локален fallback.

---

## 1. Къде реално има нужда от LLM

| Агент | Нужен ли е голям LLM? | По-евтина алтернатива |
|---|---|---|
| A2 Fetch / A3 Dedup / A5 Apply-link / A7 Aggregate / A10 Scheduler | **Не** | Чист код (regex/parsing/SQL) — 0 разход |
| A0 Profile normalize | Малко | Малък/локален модел, еднократно на профил |
| A4 Requirement extract | Малко | Малък локален модел ИЛИ правила + embeddings |
| **A6 Match scoring** | **Не** | **Embeddings + cosine similarity + keyword overlap** — почти безплатно |
| A8 Response monitor | Не/малко | Правила по имейл; малък модел само при неясен текст |
| **A9 CV / cover letter** | **Да** | Тук качеството личи → BYOK или по-голям модел |

**Ключ:** самата „намери + оцени + покажи Apply" стойност (ядрото на продукта) може да е
**напълно безплатна** — само embeddings + правила, без нито едно платено LLM извикване.

---

## 2. Embeddings за скора (най-важната икономия)

- Скорът обява↔профил = **семантична близост** → embed на изискванията и на профила,
  cosine similarity + припокриване на ключови умения.
- Модел: **локален E5 / BGE / all-MiniLM** (CPU е достатъчен). **Ти вече имаш E5/ONNX
  опит от MystyBag** — директно приложимо.
- Разход: практически 0 (само CPU на сървъра). Няма API извиквания за оценяване на
  стотици обяви.

---

## 3. Трите модела за доставяне на LLM (за A0/A4/A9)

### Вариант A — Локален малък модел (self-host)
- Llama 3.1 8B / Qwen2.5 7B / Phi през **Ollama** или llama.cpp.
- Разход: само евтин сървър (една VPS с 8–16 GB RAM; GPU по избор за скорост).
- Плюс: 0 на заявка, пълен контрол, без чужди ключове.
- Минус: по-слабо за полирани двуезични CV-та; по-бавно на CPU.

### Вариант B — API към Claude / OpenAI / Gemini (за твоя сметка)
- Плюс: най-високо качество (особено CV).
- Минус: **ти плащаш** — расте с потребителите; риск от разход. Неподходящо за безплатен
  продукт за много хора.

### Вариант C — BYOK (твоята идея, за безплатен продукт) ✅
- Потребителят въвежда **собствен API ключ** (Claude / OpenAI / Gemini / Groq / локален
  Ollama), заявките са **за негова сметка**.
- Плюс: **0 LLM разход за теб**, скалира с потребители, без per-user бюджет риск.
- Минус: триене (нужен ключ), сигурност на ключа, UX.

---

## 4. ВАЖНО уточнение (за да е реалистично)

„Да си въведат акаунта в Claude/ChatGPT" има уловка:
- **Абонамент (Claude.ai Pro / ChatGPT Plus) ≠ API ключ.** Chat абонаментът **не може** да
  се ползва програмно. За API трябва **отделен API ключ с API кредит** (Anthropic/OpenAI
  API, pay-as-you-go) — различно нещо, което casual потребител често няма.
- Затова BYOK работи най-добре ако поддържаш и **безплатни/евтини провайдъри**:
  - **Google Gemini** — има безплатен API tier (добър за старт).
  - **Groq** — много бърз, евтин/безплатен tier.
  - **Локален Ollama** — напълно безплатно, ако потребителят има машина.
  - Claude/OpenAI API — за тези, които имат ключ и искат топ качество.
- UI: „Избери провайдър + постави ключ" → тестова заявка → пазим ключа **шифрован per
  user**, никога в логове, отменим по всяко време.

---

## 5. Препоръчан модел (хибрид)

1. **Безплатно ядро (без чужди ключове, почти 0 разход за теб):**
   намиране, дедуп, валидност, **скор чрез локални embeddings**, Apply линк, списък в UI.
   Това дава основната стойност даром.
2. **Генеративно (CV/cover letter, обяснения) = BYOK:**
   потребителят си слага ключ (препоръчан безплатен Gemini/Groq tier, или свой Claude/OpenAI).
3. **Fallback:** малък **локален модел** на твоя сървър за по-скромно безплатно генериране
   на тези без ключ (ограничен лимит, за да не те натовари).

Резултат: продуктът е безплатен, ядрото не ти струва почти нищо, а скъпите заявки са или
за сметка на потребителя (BYOK), или ограничено локално.

---

## 6. Груба сметка за разход (за теб)

- **Сървър:** 1 малка VPS (embeddings + scraping + scheduler + малък локален LLM за fallback)
  — порядъка на десетки лева/месец. Основен фиксиран разход.
- **LLM API:** 0, ако ядрото е embeddings + BYOK за генериране.
- **Скалиране:** с повече потребители расте само сървърът (и то бавно, защото embeddings са
  евтини); LLM разходът остава при потребителите.
